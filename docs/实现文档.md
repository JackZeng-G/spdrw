## 1. 项目是什么

[SPD-Reader-Writer](https://github.com/1a2m3/SPD-Reader-Writer)(C# WinForms + Arduino/USB)的 Go 复刻:

- **Windows 桌面 GUI**(Wails v2 + 原生 HTML/JS/CSS,无框架)
- **去除 Arduino 串口通道**,只走主板芯片组 SMBus
- 内核访问用 **PawnIO**(签名驱动 + 签名 Pawn 模块,OpenRGB/LibreHardwareMonitor 同款),替代原版的 CPU-Z 驱动
- SPD 解析范围:DDR4/LPDDR4(X) 完整(时序/XMP 2.0/CRC)、DDR5/LPDDR5(X) 按原版同范围(身份区/EXPO/CRC)、DDR2/DDR3 基本信息

```
┌──────────────────────────────────────────────┐
│ frontend/dist  (app.js + index.html)         │  原生 JS, window.go.app.App.*
├──────────────────────────────────────────────┤
│ internal/app   App 服务层 (Wails 绑定)        │  连接/扫描/读写/写保护/解析, 对话框, 日志
├──────────────┬───────────────────────────────┤
│ internal/    │ internal/spd                  │  纯函数: dump []byte → 结构化信息
│  eeprom      │ (无 I/O, 全部可离线单测)       │
│              ├───────────────────────────────┤
│              │ internal/eeprom               │  EEPROM 协议层: 分页/整片读写/RSWP
├──────────────┴───────────────────────────────┤
│ internal/smbus Transport 接口                 │  Quick/ReadByteData/WriteByteData/...
│   ├ pawnio_backend.go  Windows: PawnIO 模块   │
│   └ fake.go            测试: 内存模拟 HUB      │
├──────────────────────────────────────────────┤
│ PawnIOLib.dll → PawnIO 驱动 → SMBus 硬件      │
└──────────────────────────────────────────────┘
```

分层原则:**每一层只认识下一层的接口**。`spd` 不做 I/O;`eeprom` 只依赖 `smbus.Transport` 接口;
`smbus` 有 Windows(PawnIO)与测试(Fake)两个实现。这使解析层可以用真实 dump 离线测试,
协议层可以用 Fake HUB 模拟 DDR4/DDR5 分页语义。

## 3. SMBus 硬件层(internal/smbus)

### 3.1 Transport 接口

```go
type Transport interface {
    Identity() (Controller, error)
    Quick(addr byte, write bool) error                  // 快速命令(DDR4 页切换用)
    ReadByteData(addr, cmd byte) (byte, error)          // 主力读:SPD 逐字节
    WriteByteData(addr, cmd, val byte) error            // DDR5 MR 写 / DDR4 字节写
    WriteByteNoData(addr byte) error                    // DDR4 SPA 页切换回退
    ReadWordData(addr, cmd byte) (uint16, error)        // 温度等 16 位寄存器
    Close() error
}
```

### 3.2 PawnIO 调用链

```
Go: session.execute("ioctl_smbus_xfer", inCells, outCells)
 → PawnIOLib.dll pawnio_execute (syscall)
 → PawnIO 驱动执行 Pawn 字节码(模块内置)
 → 硬件: IO 端口读写 SMBHSTADD/CMD/DAT0/CNT/STS
```

四个模块 ioctl:

| ioctl | 用途 | 备注 |
|---|---|---|
| `ioctl_identity` | 读控制器 PCI ID/基址 | Discover 时识别 |
| `ioctl_smbus_xfer` | 通用事务 | in=[addr,rw,cmd,protocol,data...] out=数据 |
| `ioctl_piix4_port_sel` | AMD 端口路由 | **必须给 1 格输出缓冲**(回写 old_port),否则 Win32 87 |
| `ioctl_write_protection` | I801 BIOS SPD 写禁止位 | 仅 Intel |

事务协议码:QUICK=0 BYTE=1 BYTE_DATA=2 WORD_DATA=3 BLOCK_DATA=5(i2c 块读 AMD 模块未实现)。

### 3.3 全局互斥(跨进程总线仲裁)

所有模块共享全局互斥 `Global\Access_SMBUS.HTP.Method`(Thaiphoon/OpenRGB 同款),`lockSMBus()`:

- `runtime.LockOSThread()` 包住 Wait+Release —— Windows 互斥按线程拥有,goroutine 迁移线程会把
  互斥"废弃"在别的线程上(WAIT_ABANDONED),误报"总线被占用"
- `WAIT_ABANDONED` 视为获取成功(前持有者死了,数据仍有效)
- 2 秒超时返回 nil → 上层报"请关闭 Thaiphoon/厂家工具"

### 3.4 AMD FCH (PIIX4) 多端口

- KernCZ (1022:790b) 在 00:14.0,基址硬编码 0x0B00(主库)/0x0B20(辅助)
- 端口 0/2/3/4 = 主库,经 PMIO 0xFED80300+2 位 4:3 路由;端口 1 = 0x0B20 独立控制器
- Discover 枚举全部 5 个端口会话;`piix4_smba` 是**每个 PawnIO 会话**的全局变量
- 端口路由寄存器是**全局硬件状态**:会话内只在首次事务和出错重试前重选(每字节省一次内核调用,整体耗时约减半);多会话并存/外部工具插手时靠重试路径恢复

### 3.5 错误分类(StatusToError)

NTSTATUS → 中文错误,关键映射:

| 码 | 含义 | 常见原因 |
|---|---|---|
| 0x80070002 | 找不到 PawnIO | 未装驱动 |
| 0x80070005 | 拒绝访问 | 非管理员 |
| 0x8007001F | 总线忙 | 其他程序占用 |
| 0xC00000E (NO_SUCH_DEVICE) | NACK | 地址无设备 / DDR5 HUB 拒绝 |
| 0xC00000C8+ (IO_TIMEOUT) | 事务超时 | HUB 慢/离线(模块 64ms 硬截止) |

xfer 对执行错误自动重试 3 次(间隔 5ms,重试前重选端口)——对齐原版工具"慢但能读"的宽容时序。

## 4. EEPROM 协议层(internal/eeprom)

### 4.1 两种分页语义

| | DDR4 (EE1004) | DDR5 (SPD5118 HUB) |
|---|---|---|
| 页大小 | 256B | 128B |
| 切页 | Quick 写 SPA0(0x36)/SPA1(0x37),失败回退 BYTE 写 | 写 MR11(reg 0x0B)低 3 位 |
| 页内寻址 | cmd = off 低 8 位 | cmd = (off%128) \| 0x80(**NVM 位 bit7**),bit7=0 是 MR 寄存器区 |
| 页状态可读? | 否(首读强制显式切页) | 是(回读 MR11 低 3 位) |

**DDR5 关键语义**(实机踩坑换来的):

- 地址空间 0x00-0x7F = MR 寄存器区(MR0=0x51 Device Type、MR11=页寄存器、MR12/13=RSWP 位图、MR29=I2C 写保护),0x80-0xFF = MR11 选页的 NVM 窗口
- **MR0 读出 0x51 是寄存器不是 NVM**;NVM 页 0 的 byte0 是 0x30(DDR5 头部:用 512B/共 1024B/rev1.2),**不要**拿 0x51 当 NVM 头校验
- **HUB 的 MR11 可能有 BIOS 残留值**(如 5/7)——New 时回读 MR11 同步缓存,不假设页 0;每次切页后回读校验,失败重试一次。这修掉了"读出几乎全 0+零星真数据"的乱页问题
- MR 写是寄存器写,无需 EE1004 式 25ms 写周期;逐字节读间 1ms(对齐 RAMSPDToolkit SPD_IO_DELAY),HUB 对背靠背事务敏感

### 4.2 主要 API

```go
d, _ := eeprom.New(transport, 0x50)   // 探测+识别 DDR5/大小(探测阶段零写操作)
data, _ := d.ReadAll()                // 整片(自动分页)
d.Write(dump, force, progressFn)      // 增量写(跳过同值)+逐字节回读校验
d.Verify(dump)                        // 比对当前内容
d.RSWPStatus() / RSWPSet(blk) / RSWPClear()   // DDR4 quick 命令 / DDR5 MR12/13 位图
d.PSWPStatus()                        // 只检测;永久保护需高压编程器,不做
```

写延时:对 0x50-0x57 的写事务统一 25ms 后置(EE1004 写周期,原版同款;DDR5 MR 写也走它,保守无害)。

## 5. SPD 解析层(internal/spd)

纯函数、无 I/O、全离线可测(`realworld_test.go` 用实机 16GiB 1Rx8 SODIMM 的字节做回归)。

- `Identify(dump)` → RamType + 应有长度(byte0/1 尺寸码,DDR5 看 byte2==0x12)
- `Crc16` SPD CRC-16(CCITT,DDR4/5 校验覆盖区各代不同);`ValidateSpd` 完整性检查
- `ManufacturerName(cont, code)` — JEDEC 厂商库从原版 Resources.cs 提取,`go:embed` 内嵌
- **位域提取一律走 `subByteR(v, pos, cnt)`** = 原版 C# `Data.SubByte` 语义
  (`bits[pos-cnt+1..pos]`,pos 是高位端),移植字段时直接抄原版调用参数,不要手工换算
- DDR4:byte6 密度/ banks、byte5 行列、byte12 组织、byte13 总线宽、时序表(NT/MT/FT 三粒度)、CAS 掩码 4 字节、XMP 2.0(0x2DC 起)
- DDR5:byte4 密度×die、byte6 I/O 宽(bits[7:5],`4<<code` = x4/x8/x16/x32)、byte234 组织(ranks=bits[5:3]+1)、byte235 通道(bits[6:5],`1<<code`)×每通道位宽(bits[2:0],`1<<(code+3)`,0x22=2 通道×32bit)、身份区 512-640(厂商 0x200/日期 0x203/序列号 0x205/部件号 0x209)、EXPO 存在性(0x280 起)
- **容量单位陷阱**:`DDR5SPD.TotalCapacityBytes()` 返回的实际是 **GiB**(原版公式直接出 GiB),调用方 `*1024` 得 MiB —— 函数名有历史包袱,已在注释标明

## 6. 服务层与前端(internal/app + frontend/dist)

### 6.1 Wails 绑定要点(踩坑实录)

- **构建必须带 `-tags desktop,production`**,否则启动弹 Wails 保护错误框
- **绑定方法最多 2 个返回值**,3 个返回值的方法静默返回 null(`(int, []DimmInfo, error)` → 前端永远拿到 null);多值用单结构体 + 小写 json tag(`AutoConnectResult{ctlIndex, dimms}`)
- **v2 的 JS 运行时没有对话框 API**(`window.runtime` 只有事件/窗口/剪贴板等)——`SaveFileDialog`/`OpenFileDialog` 必须从 **Go 侧** `runtime.SaveFileDialog(ctx, ...)` 调用;本项目把对话框函数注入 `App.SaveDialog/OpenDialog` 字段,OnStartup 时用 ctx 闭包填充
- **Go `[]byte` 跨序列化是 base64 字符串**(双向对称:JSON 的 []byte 编解码即 base64):前端渲染前必须 `atob` 解码,否则把 base64 字符当字节渲染出"0G/0M"这类鬼字符;**前端向后端传二进制也保持 base64 字符串原样传**,不要 JSON.stringify(Uint8Array)(会变对象导致解码失败)
- 绑定键 = 绑定结构体的包名:`window.go.app.App.*`(不是 main.App);等 `window.go.app` 就绪后再初始化 UI
- UI 流程(用户确认的交互契约):**启动=连接+扫描+空白待选**(设备下拉首项" — 请选择 —"占位,不自动读取);用户选中才读取;无独立读取按钮;"重扫设备"回空白待选;保存走后端 dump 缓存(绕开 JS 传大数据)

### 6.2 绑定方法一览(App)

| 方法 | 签名要点 | 说明 |
|---|---|---|
| `ListControllers` | `[]ControllerInfo` | 枚举(含管理员/PawnIO 检测的错误文案) |
| `AutoConnectAll` | `*AutoConnectResult` | 逐控制器 Connect+Scan,停在第一个有设备的 |
| `Connect` / `Scan` / `Select` | index / `[]DimmInfo` / addr | 基础流程;Scan 逐地址探测+错误分类日志 |
| `Dump` | `[]byte`(base64) | 整片读取;DDR5 后附单行 HUB 诊断(MR0/3/11/29/48) |
| `SaveDumpDialog` | error | Go 弹保存框 → 写后端缓存的 dump(lastDump,Select 时失效) |
| `DecodeFileDialog` | `*DecodeResult`(含 path) | Go 弹打开框 → 离线解析 |
| `VerifyFileDialog` / `WriteFileDialog` | `(path, error)` | 校验/写入,写后前端自动重读 |
| `WPStatus` / `WPSet` / `WPClear` | | RSWP 位图/按块设置/清除(4 返回值的方法用闭包拆分调用) |
| `Decode` / `DecodeFile` / `ReadFileBytes` | | 离线解析与文件读取(非 Windows 平台也能用) |

### 6.3 事件

`log`(time+text 日志行)、`dump:done`(字节数)、`write:progress`(写入进度)——前端 `EventsOn` 订阅。

## 9. 真机调试经验(按时间序,遇同类问题先查这里)

1. **Win32 87 (INVALID_PARAMETER)**:PIIX4 端口选择 ioctl 缺输出缓冲 → 补 1 格 `selOut`
2. **Win32 433 (NO_SUCH_DEVICE)**:把 DDR5 误判成 DDR4 后写 0x36 被拒 → 探测阶段零写、DDR5 以 MR0==0x51 判定
3. **启动挂死**:探测阶段做 MR 写 + 互斥无限等 → 零写探测 + 2s 互斥超时
4. **"总线被占用"误报**:互斥跨线程废弃 → LockOSThread + WAIT_ABANDONED=成功
5. **hex 表出现 0G/0M 之类**:把 base64 字符串当字节渲染(见 §6.1)→ `atob` 解码
6. **dump 几乎全 0 + 零星真数据 + CRC 失败**:MR11 残留页(见 §4.1)→ 回读同步 + 切页校验
7. **读全对但解析 0bit/0MiB**:字段没填(DDR5 deviceWidth)或单位错(GiB≠Bytes),用实机样本回归测试锁行为
8. **保存/打开按钮无反应**:v2 JS 无对话框 API(见 §6.1)→ Go 侧实现
9. **慢(32s/dump)**:每字节 2 次内核调用(端口重选+事务)→ 端口只在首次/重试前重选,约减半;进一步提速需块读,但 AMD 模块未实现 I2C 块读协议,SPD5118 的 SMBus 块读支持未验证,暂缓

## 9.5 写入护栏与 SPD 编辑器(2026-09-21 增补)

### 写入路径(唯一可能变砖的操作)

流程: `PickWriteFile` → `PreflightWrite` → `WriteConfirmed`(编辑器走 `EditApplyToDevice`)。

- **计划**: `eeprom.PlanWrite` 生成逐字节 diff, 排序上把 **CRC 字节放到最后** ——
  写入中断时设备上是"CRC 与数据不符"(BIOS 会拒绝该条), 而不是"校验通过但内容错"。
- **长度**: 必须等于 SPD 大小(旧实现 `dump[:size]` 在长度不足时切片越界 panic)。
- **中止语义**: `WriteError{Offset, Written, Total, Stage}` 明确"已写/未写多少 + 建议用备份恢复"。
- **预检**: 目标 dump CRC 必须有效、受保护块与变更块相交即拒绝、高危字段(容量/组织/电压/PMIC)
  单独列出、`SizeOK`、PSWP。
- **备份**: 真实写入前把设备当前整片存到 `~/.spdrw/backups/spd-<addr>-<时间>.bin`。
- **确认**: 服务层强制确认串(`WRITE` / 干跑 `DRYRUN`); UI 层要求勾选"我已另有备份"并显示 diff 面板。
- **干跑**: `eeprom.SetDryRun(true)` 后所有写只落内存影子(`ShadowImage()` 可查看结果),
  用于真机上零风险跑通整条写入流程。

### 编辑器

`spd.Editor` 是纯内存编辑视图(原始副本 + 工作副本 + 变更表), `Fields()`/`SetField()` 是
字段模型的唯一入口 —— Wails 只需绑定两个方法, 新增字段不必改接口。

- 字段元数据: key / 名称 / 分组(常用信息 / JEDEC 时序 / XMP 2.0 / XMP 3.0 / EXPO) /
  类型(int,float,string,hex,bool) / 单位 / 范围 / 当前值 / 偏移 / 风险 / 说明。
- 字符串字段填充沿用原始 dump 的填充字符(0x00 或 0x20), 保证"改回原值后逐字节一致"。
- CRC 由编辑器重算(`FixCRC`), 写入前必须 `CRCOK()` 通过。
- 扩展区: XMP 2.0(DDR4 384 起 2×63B)、XMP 3.0(header 0x280 + 槽 0x2C0..0x3C0)、
  EXPO(0x340-0x3BF, 与 XMP 槽 3/User1 互斥)。
- 原始 hex 编辑走 `SetByte(off, val)`(高风险, UI 单列)。

### 字段偏移修正(与原版 C# 移植版不同之处)

| 项 | 旧实现 | 现实现 |
|---|---|---|
| DDR5 XMP 3.0 槽位 | `0x280 + i*64`(把 header 当第一槽, 漏检 0x3C0) | `0x2C0/0x300/0x340/0x380/0x3C0`, 补 header CRC, EXPO 时跳过槽 3/User1 |
| DDR2 总线/芯片位宽 | byte8(接口电压)/byte6(模块数据宽度) | byte6(屏蔽 ECC 低 4 位)/byte13 |
| DDR2 校验 | 按"DDR2 无 CRC"恒真 | byte63 = sum(0..62) |
| DDR5 时序 | 不解析 | byte 20-102 全解析 |

## 10. 已知限制与后续方向

- AMD 模块无 I2C_BLOCK_DATA 协议;若将来验证 SPD5118 支持 SMBus 块读(0x14),可实现 32B/事务,读取从 ~15s 降到 <1s
- SKX (Skylake-SP IMC) 与 I801 路径代码完成但未上真机验证
- PSWP 仅检测(与原版 SMBus 路径一致);DDR5 RSWP 清除部分平台需离线模式/断电
- 读取速度受逐字节事务限制;解析层、写保护、文件链路与真机验证清单见 `docs/验证清单.md`
