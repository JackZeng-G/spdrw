## 1. 项目是什么

**独立实现的 Windows SPD 读写工具**(未使用上游代码, 见 README 的定位说明)。
编码 SPD 字段与时序语义时, 以 [SPD-Reader-Writer](https://github.com/1a2m3/SPD-Reader-Writer)
(C# WinForms + Arduino/USB)为**对照参照**(仅字段定义与操作思路):

- **Windows 桌面 GUI**(Wails v2 + 原生 HTML/JS/CSS,无框架)
- **去除 Arduino 串口通道**,只走主板芯片组 SMBus
- 内核访问用 **PawnIO**(签名驱动 + 签名 Pawn 模块,OpenRGB/LibreHardwareMonitor 同款),替代参考项目依赖的 CPU-Z 驱动
- SPD 解析范围:DDR4/LPDDR4(X) 完整(时序/XMP 2.0/CRC)、DDR5/LPDDR5(X) 与参考项目同范围(身份区/EXPO/CRC)、DDR3 基本信息。**DDR2 不再支持**(太老、公开渠道没有任何真实 dump 可验证, 2026-09-21 移除; byte2=0x08-0x0A 按"未知类型"拒绝)

```
┌──────────────────────────────────────────────┐
│ frontend/dist  (app.js + index.html)         │  原生 JS, window.go.app.App.*
├──────────────────────────────────────────────┤
│ internal/app   App 服务层 (Wails 绑定)        │  连接/扫描/读写/写保护/解析, 对话框, 日志
├──────────────┬───────────────────────────────┤
│ internal/    │ internal/spd                  │  纯函数: dump []byte → 结构化信息
│  eeprom      │ (无 I/O, 全部可离线单测)       │
│              ├───────────────────────────────┤
│              │ internal/eeprom               │  EEPROM 协议层: 分页/整片读写/RSWP
├──────────────┴───────────────────────────────┤
│ internal/smbus Transport 接口                 │  Quick/ReadByteData/WriteByteData/...
│   ├ pawnio_backend.go  Windows: PawnIO 模块   │
│   └ fake.go            测试: 内存模拟 HUB      │
├──────────────────────────────────────────────┤
│ PawnIOLib.dll → PawnIO 驱动 → SMBus 硬件      │
└──────────────────────────────────────────────┘
```

分层原则:**每一层只认识下一层的接口**。`spd` 不做 I/O;`eeprom` 只依赖 `smbus.Transport` 接口;
`smbus` 有 Windows(PawnIO)与测试(Fake)两个实现。这使解析层可以用真实 dump 离线测试,
协议层可以用 Fake HUB 模拟 DDR4/DDR5 分页语义。

## 3. SMBus 硬件层(internal/smbus)

### 3.1 Transport 接口

```go
type Transport interface {
    Identity() (Controller, error)
    Quick(addr byte, write bool) error                  // 快速命令(DDR4 页切换用)
    ReadByteData(addr, cmd byte) (byte, error)          // 主力读:SPD 逐字节
    WriteByteData(addr, cmd, val byte) error            // DDR5 MR 写 / DDR4 字节写
    WriteByteNoData(addr byte) error                    // DDR4 SPA 页切换回退
    ReadWordData(addr, cmd byte) (uint16, error)        // 温度等 16 位寄存器
    Close() error
}
```

### 3.2 PawnIO 调用链

```
Go: session.execute("ioctl_smbus_xfer", inCells, outCells)
 → PawnIOLib.dll pawnio_execute (syscall)
 → PawnIO 驱动执行 Pawn 字节码(模块内置)
 → 硬件: IO 端口读写 SMBHSTADD/CMD/DAT0/CNT/STS
```

四个模块 ioctl:

| ioctl | 用途 | 备注 |
|---|---|---|
| `ioctl_identity` | 读控制器 PCI ID/基址 | Discover 时识别 |
| `ioctl_smbus_xfer` | 通用事务 | in=[addr,rw,cmd,protocol,data...] out=数据 |
| `ioctl_piix4_port_sel` | AMD 端口路由 | **必须给 1 格输出缓冲**(回写 old_port),否则 Win32 87 |
| `ioctl_write_protection` | I801 BIOS SPD 写禁止位 | 仅 Intel |

事务协议码:QUICK=0 BYTE=1 BYTE_DATA=2 WORD_DATA=3 BLOCK_DATA=5 I2C_BLOCK_DATA=8。
PIIX4 模块实现了 BLOCK_DATA(模块内按 33 字节打包成 5 个 cell),I801 模块两者都实现;
但真机 FCH+HUB 上 BLOCK_DATA 被 NACK,实际走 WORD_DATA(详见 §9 第 9 条)。

### 3.3 全局互斥(跨进程总线仲裁)

所有模块共享全局互斥 `Global\Access_SMBUS.HTP.Method`(Thaiphoon/OpenRGB 同款),`lockSMBus()`:

- `runtime.LockOSThread()` 包住 Wait+Release —— Windows 互斥按线程拥有,goroutine 迁移线程会把
  互斥"废弃"在别的线程上(WAIT_ABANDONED),误报"总线被占用"
- `WAIT_ABANDONED` 视为获取成功(前持有者死了,数据仍有效)
- 2 秒超时返回 nil → 上层报"请关闭 Thaiphoon/厂家工具"

### 3.4 AMD FCH (PIIX4) 多端口

- KernCZ (1022:790b) 在 00:14.0,基址硬编码 0x0B00(主库)/0x0B20(辅助)
- 端口 0/2/3/4 = 主库,经 PMIO 0xFED80300+2 位 4:3 路由;端口 1 = 0x0B20 独立控制器
- Discover 枚举全部 5 个端口会话;`piix4_smba` 是**每个 PawnIO 会话**的全局变量
- 端口路由寄存器是**全局硬件状态**:会话内只在首次事务和出错重试前重选(每字节省一次内核调用,整体耗时约减半);多会话并存/外部工具插手时靠重试路径恢复

### 3.5 错误分类(StatusToError)

NTSTATUS → 中文错误,关键映射:

| 码 | 含义 | 常见原因 |
|---|---|---|
| 0x80070002 | 找不到 PawnIO | 未装驱动 |
| 0x80070005 | 拒绝访问 | 非管理员 |
| 0x8007001F | 总线忙 | 其他程序占用 |
| 0xC00000E (NO_SUCH_DEVICE) | NACK | 地址无设备 / DDR5 HUB 拒绝 |
| 0xC00000C8+ (IO_TIMEOUT) | 事务超时 | HUB 慢/离线(模块 64ms 硬截止) |

xfer 对执行错误自动重试 3 次(间隔 5ms,重试前重选端口)——对齐参考项目工具"慢但能读"的宽容时序。

## 4. EEPROM 协议层(internal/eeprom)

### 4.1 两种分页语义

| | DDR4 (EE1004) | DDR5 (SPD5118 HUB) |
|---|---|---|
| 页大小 | 256B | 128B |
| 切页 | Quick 写 SPA0(0x36)/SPA1(0x37),失败回退 BYTE 写 | 写 MR11(reg 0x0B)低 3 位 |
| 页内寻址 | cmd = off 低 8 位 | cmd = (off%128) \| 0x80(**NVM 位 bit7**),bit7=0 是 MR 寄存器区 |
| 页状态可读? | 否(首读强制显式切页) | 是(回读 MR11 低 3 位) |

**DDR5 关键语义**(实机踩坑换来的):

- 地址空间 0x00-0x7F = MR 寄存器区(MR0=0x51 Device Type、MR11=页寄存器、MR12/13=RSWP 位图、MR29=I2C 写保护),0x80-0xFF = MR11 选页的 NVM 窗口
- **MR0 读出 0x51 是寄存器不是 NVM**;NVM 页 0 的 byte0 是 0x30(DDR5 头部:用 512B/共 1024B/rev1.2),**不要**拿 0x51 当 NVM 头校验
- **HUB 的 MR11 可能有 BIOS 残留值**(如 5/7)——New 时回读 MR11 同步缓存,不假设页 0;每次切页后回读校验,失败重试一次。这修掉了"读出几乎全 0+零星真数据"的乱页问题
- MR 写是寄存器写,无需 EE1004 式 25ms 写周期;逐字节读间 1ms(对齐 RAMSPDToolkit SPD_IO_DELAY),HUB 对背靠背事务敏感

### 4.2 主要 API

```go
d, _ := eeprom.New(transport, 0x50)   // 探测+识别 DDR5/大小(探测阶段零写操作)
data, _ := d.ReadAll()                // 整片(自动分页)
d.Write(dump, force, progressFn)      // 增量写(跳过同值)+逐字节回读校验
d.Verify(dump)                        // 比对当前内容
d.RSWPStatus() / RSWPSet(blk) / RSWPClear()   // DDR4 quick 命令 / DDR5 MR12/13 位图
d.PSWPStatus()                        // 只检测;永久保护需高压编程器,不做
```

写延时:对 0x50-0x57 的写事务统一 25ms 后置(EE1004 写周期,参考项目同款;DDR5 MR 写也走它,保守无害)。

## 5. SPD 解析层(internal/spd)

纯函数、无 I/O、全离线可测(`realworld_test.go` 用实机 16GiB 1Rx8 SODIMM 的字节做回归)。

- `Identify(dump)` → RamType + 应有长度(byte0/1 尺寸码,DDR5 看 byte2==0x12)
- `Crc16` SPD CRC-16(CCITT,DDR4/5 校验覆盖区各代不同);`ValidateSpd` 完整性检查
- `ManufacturerName(cont, code)` — JEDEC 厂商库从参考项目 Resources.cs 提取(仅数据, 见 internal/spd/data/README.md),`go:embed` 内嵌
- **位域提取一律走 `subByteR(v, pos, cnt)`** = 参考项目 C# `Data.SubByte` 的语义
  (`bits[pos-cnt+1..pos]`,pos 是高位端),对照字段时沿用同一套位域参数(位置/位数直接照搬文档值),不要手工换算
- DDR4:byte6 密度/ banks、byte5 行列、byte12 组织、byte13 总线宽、时序表(NT/MT/FT 三粒度)、CAS 掩码 4 字节、XMP 2.0(0x2DC 起)
- DDR5:byte4 密度×die、byte6 I/O 宽(bits[7:5],`4<<code` = x4/x8/x16/x32)、byte234 组织(ranks=bits[5:3]+1)、byte235 通道(bits[6:5],`1<<code`)×每通道位宽(bits[2:0],`1<<(code+3)`,0x22=2 通道×32bit)、身份区 512-640(厂商 0x200/日期 0x203/序列号 0x205/部件号 0x209)、EXPO 存在性(0x280 起)
- **容量单位陷阱**:`DDR5SPD.TotalCapacityBytes()` 返回的实际是 **GiB**(参考项目公式直接出 GiB),调用方 `*1024` 得 MiB —— 函数名有历史包袱,已在注释标明

## 6. 服务层与前端(internal/app + frontend/dist)

### 6.1 Wails 绑定要点(踩坑实录)

- **构建必须带 `-tags desktop,production`**,否则启动弹 Wails 保护错误框
- **绑定方法最多 2 个返回值**,3 个返回值的方法静默返回 null(`(int, []DimmInfo, error)` → 前端永远拿到 null);多值用单结构体 + 小写 json tag(`AutoConnectResult{ctlIndex, dimms}`)
- **v2 的 JS 运行时没有对话框 API**(`window.runtime` 只有事件/窗口/剪贴板等)——`SaveFileDialog`/`OpenFileDialog` 必须从 **Go 侧** `runtime.SaveFileDialog(ctx, ...)` 调用;本项目把对话框函数注入 `App.SaveDialog/OpenDialog` 字段,OnStartup 时用 ctx 闭包填充
- **Go `[]byte` 跨序列化是 base64 字符串**(双向对称:JSON 的 []byte 编解码即 base64):前端渲染前必须 `atob` 解码,否则把 base64 字符当字节渲染出"0G/0M"这类鬼字符;**前端向后端传二进制也保持 base64 字符串原样传**,不要 JSON.stringify(Uint8Array)(会变对象导致解码失败)
- 绑定键 = 绑定结构体的包名:`window.go.app.App.*`(不是 main.App);等 `window.go.app` 就绪后再初始化 UI
- UI 流程(用户确认的交互契约):**启动=连接+扫描+空白待选**(设备下拉首项" — 请选择 —"占位,不自动读取);用户选中才读取;无独立读取按钮;"重扫设备"回空白待选;保存走后端 dump 缓存(绕开 JS 传大数据)

### 6.2 绑定方法一览(App)

**绑定面 = 31 个导出方法**(2026-09-21 从 50 个收敛; 前端实际调用 29 个), 剩下的都是必须暴露给
前端的入口。曾经的"文件路径"两层 API(SaveDumpDialog→SaveDump、DecodeFileDialog→DecodeFile、
PickWriteFile、ReadFileBytes、SaveDumpData)已删除, 因为界面改成"编辑器是唯一入口":
打开文件走 `EditLoadFileDialog`、导出走 `EditExportDialog`、校验走 `VerifyFileDialog`。

> **写过设备的关键入口改为包内方法**(不再是对外绑定): `writeConfirmed` / `preflightWrite`。
> 它们按**文件路径**写设备, 留着就等于前端还有第二条绕过编辑器的写入路径;
> 包内保留是因为安全流水线(门禁/备份/回读/回滚)的用例都通过它们驱动。
> 同理包内化的还有 `busStats` / `logEntries` / `closeDevice` / `saveDump` / `decodeFile` /
> `verifyFile` / `editLoadPath` —— 它们是"被更外层的绑定调用"或"只给测试用"的内部入口。
>
> 判定手法: 前端 `call("X")` 名单 ∩ 导出方法名 = 必须暴露的; 其余按"有没有 Go 调用方"
> 决定删掉还是包内化。`deadlock_test.go` 的入口清单要同步(它覆盖所有持锁入口, 含包内)。

| `ListControllers` | `[]ControllerInfo` | 枚举(含管理员/PawnIO 检测的错误文案); 只列探测到设备的控制器 |

### 6.4 界面结构(2026-09-21 重整)

`frontend/dist/` 是手工维护的三件套(无构建工具): `index.html` 结构 + `style.css` 样式 + `app.js` 逻辑。
改样式的约束写在测试里(`frontend/test/page.test.mjs`): app.js 里 `$("id")` 用到的元素必须在 index.html 存在、
hex 列头与行偏移必须 sticky、图例色块必须与格子里用的是同一份色值 —— 动 UI 后先跑 `node --test "frontend/test/*.test.mjs"`。

**设计令牌**: `style.css` 顶部按"表面 → 语义 → 组件"三层定义变量, 组件规则只引用变量、不写字面色值。
字体走系统栈(`Segoe UI Variable/Segoe UI` + `Cascadia Mono/Consolas`), **不引 Google Fonts**:
这是离线桌面程序, WebView2 里没有"一定能联网"这个前提。

**hex 区域色带**(左侧 SPD 内容视图的底色):

- 数据来源**不是硬编码的 JEDEC 规范**, 而是两处已有的运行时数据:
  ① `CRCStatus` 返回的 `ranges`(参与校验的区段)与 `freeAreas`(不参与校验的自由区);
  ② `EditFields` 每个字段的 `offset`, 映射到具体字节后在悬停时显示字段名。
  于是 DDR3/4/5 自动适配, 规范修订或字段增删都不会让色带失真。
- 字段 offset 有四种文本形态, 由 `parseFieldSpans()` 解析(认不出的片段跳过, 不能让一个怪 offset 把渲染搞坏):
  `0x050`(单字节) / `0x140-0x141`(起-止) / `0x149-20B`(起+长度) / `0x18/0x7B`(多处, 用 `/` 分隔)。
- 色带语义: 蓝=参与校验, 绿=不参与校验, 紫=身份信息, 青=JEDEC 时序, 黄=XMP/EXPO;
  与"改动标记"(红底=影响校验、蓝底=不影响、黄框=CRC 值本身)是**两套正交的视觉信号**, 图例在 hex 标题的"?"里。
- 刷新时机: 区域数据(`CRCStatus`)比字节到手晚, 所以色带在 `applyHexMarks()` 里补刷(只切 class 不重绘),
  不能在 `renderHex()` 里一次做完。

**XMP 3.0 槽位卡片**(信息面板):

- 布局: header(0x280) + 5 个 64B 槽(0x2C0/0x300/0x340/0x380/0x3C0) = 3 份 Profile + 2 份 User;
  AMD EXPO(0x340 起 128B) 与槽 3 / User 1 重叠, 这两张卡显示为"EXPO 占用"而不是空槽。
- **数据不来自 `Decode`**, 而是编辑器字段列表里 group = `XMP 3.0` 的那批(`EditFields`): 后端
  (`internal/spd/editor_profiles.go` 的 `xmp3ProfileSpecs`)已经把每槽的电压/时序解成字段,
  前端只做"按槽聚合 + 展示"(`collectXmp3` / `renderXmp3SlotGrid`)—— 解析规则的唯一真相留在后端,
  前端不重复解析 dump。
- 因为字段比 `Decode` 晚一步到手, 信息面板是**两段式渲染**: `decodeCurrent()` 先画(此时退回一行式简表),
  `adoptDeviceEditor()` 拉到字段后调 `rerenderInfo()` 用缓存的 `lastDecode` 重画成槽位卡片。
- 展示: 槽名 + profile 名称 + 启用徽章; 关键行 tCK(换算 `ns → MHz → MT/s`, DDR 双沿)与 CL 掩码;
  其余时序两列表格; 电压(VDD/VDDQ/VPP/VMEMCTRL)单列一行。空槽用虚线框, 一眼区分"没写"和"写了没启用"。
- 回归测试在 `frontend/test/xmp3.test.mjs`(槽位数/槽名/换算/空槽/EXPO 占用/无字段时回退简表)。

**信息面板: 默认窗口一屏看全**(用户目标 —— "默认应用窗口能把所有信息显示全", 编辑器页不在此列)

- 字号: 正文 13px、次级 12px、小字 11px, 控件高 26px; **JEDEC/时序表再降一档用 11px**(`--fs-xs`)
  并压紧行距(`padding: 1px 5px; line-height: 1.4`)—— 这是"24 项双列还要显示全"的关键。
- 信息面板宽度 `clamp(400px, 48%, 700px)`: 默认窗口(1200)下面板 ≈576px, 刚好让时序表**双列**放得下。
- 概要卡片改成**键值对两列并排**(`.kv` 四列网格, 每行两组), 纵向省一半; 面板窄(≤1180 视口)时用媒体查询退回单列。
- 卡片与面板留白收紧(`.info-body` padding 8/10、gap 8; `.card-head` 4px; 卡片体 6/10)。
- 实测(表格宽 + 内容总高 vs 可用高度, 面板 575px 等价 1198 窗口):
  24 项双列 = 12 行, 表格 518px < 卡片 542px(不横向溢出), 表格高 226px,
  **信息内容总高 474px** ≤ 默认 1200x800 窗口的可用 482px(800 − 顶栏 44 − 日志 10 行 240 − tabs 34),
  用户实际用的 1198x1042 窗口可用 722px 更宽松。
- **时序表列数自适应**: `timingCols()` 按信息面板实际宽度决定(≥560px 两列, 否则一行一组, 窄窗口不至于横向滚动),
  `timingRowsHTML()` 据此生成行; 窗口 resize 后若列数会变, 200ms 防抖调 `rerenderInfo()` 重画。
- `lower limit` 在表格里简写为 `↓6`(原 `(下限 6)`), 让双列在 576px 面板里放得下; 语义是
  JEDEC 把这类时序(tRRD_L/tCCD_L/tFAW/…)定义成**周期数**: SPD 同时存"按本模组 tCKmin 折算的
  时间"与"周期下限", 生效值 = max(时间, 下限×tCK), 内存控制器换时钟频率时按下限重算。
  语料核验: tFAW 下限恒为 32(=32nCK), 416ps 条存 13.33ns、357ps 条存 11.43ns, 都恰好 32×tCK。
- 下拉框在窄窗口必然截断(控制器名很长), 完整文本挂在 `select.title` 上(`syncSelectTitle()`), 悬停可看全。

**日志面板高度可调**: 默认高度 = 标题栏 + **10 行**日志(`LOG_ROWS_DEFAULT`), 由 `measureDefaultLogHeight()`
用真实行高实测(字号改了不用跟着改数字); 顶部把手(`log-resizer`, `role="separator"`, 可聚焦)上下拖动改高;
高度写进 CSS 变量 `--log-h` 并存 `localStorage`(`spdrw.logHeight`)供下次启动恢复; 双击复位, 聚焦后
↑/↓ 步进(Shift 加速), Home 复位; 从折叠态开始拖会先展开到记忆高度(`logHeightExpanded`),
不会把人拖回一个 34px 的面板。

**其它**: 日志面板可折叠(`btn-log-toggle`)、可清空, 只保留最近 400 条(长时间跑总线不该让 DOM 无限长大);
字段输入框获得焦点时, 左侧 hex 里对应字节会闪烁高亮(`flashField()`); 空状态统一用 `.empty-state`。

## 9. 真机调试经验(按时间序,遇同类问题先查这里)

1. **Win32 87 (INVALID_PARAMETER)**:PIIX4 端口选择 ioctl 缺输出缓冲 → 补 1 格 `selOut`
2. **Win32 433 (NO_SUCH_DEVICE)**:把 DDR5 误判成 DDR4 后写 0x36 被拒 → 探测阶段零写、DDR5 以 MR0==0x51 判定
3. **启动挂死**:探测阶段做 MR 写 + 互斥无限等 → 零写探测 + 2s 互斥超时
4. **"总线被占用"误报**:互斥跨线程废弃 → LockOSThread + WAIT_ABANDONED=成功
5. **hex 表出现 0G/0M 之类**:把 base64 字符串当字节渲染(见 §6.1)→ `atob` 解码
6. **dump 几乎全 0 + 零星真数据 + CRC 失败**:MR11 残留页(见 §4.1)→ 回读同步 + 切页校验
7. **读全对但解析 0bit/0MiB**:字段没填(DDR5 deviceWidth)或单位错(GiB≠Bytes),用实机样本回归测试锁行为
8. **保存/打开按钮无反应**:v2 JS 无对话框 API(见 §6.1)→ Go 侧实现
9. **慢(32s/dump)**:实测瓶颈是 HUB 侧每次 SMBus 事务的固有延迟(1024 事务 ≈ 32s ≈ 31ms/次),软件层的 `ReadDelay` 只占约 1s。因此**唯一有效手段是减少事务数**,实现为三级自适应读路径:
   - 块读 `I2C_SMBUS_BLOCK_DATA(5)` 32B/事务 → AMD PIIX4 模块实现了该协议,但真机(FCH + DDR5 HUB)返回 NACK,**不可用**;
   - 字读 `WORD_DATA(3)` 2B/事务 → 可用,1024B 约 512 次事务 ≈ 16s;
   - 逐字节 `BYTE_DATA(2)` 1B/事务 ≈ 32s(兜底)。
   每级都先**只读探测**(与下一级读法比对,不写总线),失败即降级并记住结论;页边界不跨读(字读不跨页)。日志与界面显示实际档位、事务数、耗时、回退原因。

## 9.5 写入护栏与 SPD 编辑器(2026-09-21 增补)

### 写入路径(唯一可能变砖的操作)

流程: 界面唯一入口是 `EditApplyToDevice`(编辑器内容直接写);按文件路径的 `writeConfirmed`
与纯预览的 `preflightWrite` 已**包内化**(不给前端第二条写入路径), 由安全流水线测试驱动。
三条路共用同一套 `buildPreflight`(预检)+ `writeWithPreflight`(写入)内核。

- **计划**: `eeprom.PlanWrite` 生成逐字节 diff, 排序上把 **CRC 字节放到最后** ——
  写入中断时设备上是"CRC 与数据不符"(BIOS 会拒绝该条), 而不是"校验通过但内容错"。
- **长度**: 必须等于 SPD 大小(旧实现 `dump[:size]` 在长度不足时切片越界 panic)。
- **中止语义**: `WriteError{Offset, Written, Total, Stage}` 明确"已写/未写多少 + 建议用备份恢复"。
- **预检**: 目标 dump CRC 必须有效、受保护块与变更块相交即拒绝、高危字段(容量/组织/电压/PMIC)
  单独列出、`SizeOK`、PSWP。
- **备份**: 真实写入前把设备当前整片存到**程序同级** `backup\spd-<addr>-<时间>.bin`
  (目录自动创建; v1.0.0 及之前在 `~/.spdrw/backups`)。目录创建/写入失败 → 写入在动设备
  之前就中止 —— 宁可不写, 不能没备份。保留最近 20 份, 超出按时间戳清理
  (临时文件 + fsync + rename + 回读校验, 只保留最近 20 份)。
- **确认**: 服务层强制确认串(`WRITE` / 干跑 `DRYRUN`); UI 层没有"干跑"与"我已另有备份"
  勾选(备份每次自动做), 写入前的 diff 面板就是预检面板。
- **总线计数**: 每个控制器外面套一层 `smbus.CountingTransport`(只转发+计数, 不改语义),
  干跑结果与日志会报出"读 / 页选择与命令写 / 字节写 / 其中 NVM 数据写"四项。
  真机验证 V2 就是靠这行数字证明 SPD 没被碰过 —— 光说"代码里没写"不算证据。
  统计随写入结果(`WriteResult.BusStats`)返回;曾经的 `BusStats`/`ResetBusStats` 导出绑定
  已随绑定面收敛(包内化/删除), 界面不再单独读数。NVM 写的判定按世代: DDR5 看 cmd bit7(CHUB 寄存器/切页是 bit7=0),
  DDR4 及更早看地址是否落在 0x50-0x57(quick 与 0x30-0x37 的页选择/PSWP 探测不算 NVM 写)。
- **干跑**: `eeprom.SetDryRun(true)` 后所有写只落内存影子(`ShadowImage()` 可查看结果),
  用于真机上零风险跑通整条写入流程。阻断分两类(`WritePreflight.BlockKind`):
  `size`/`crc` 是"数据本身不合格"(干跑也拒绝), `protected`/`pswp` 是"硬件此刻不接受"
  (干跑只做内存演算, 放行并在消息里带提示)。

### 编辑器

`spd.Editor` 是纯内存编辑视图(原始副本 + 工作副本 + 变更表), `Fields()`/`SetField()` 是
字段模型的唯一入口 —— Wails 只需绑定两个方法, 新增字段不必改接口。

- 字段元数据: key / 名称 / 分组(常用信息 / JEDEC 时序 / XMP 2.0 / XMP 3.0 / EXPO) /
  类型(int,float,string,hex,bool) / 单位 / 范围 / 当前值 / 偏移 / 风险 / 说明。
- 字符串字段填充沿用原始 dump 的填充字符(0x00 或 0x20), 保证"改回原值后逐字节一致"。
- CRC 由编辑器重算(`FixCRC`), 写入前必须 `CRCOK()` 通过。
- 扩展区: XMP 2.0(DDR4 384 起 2×63B)、XMP 3.0(header 0x280 + 槽 0x2C0..0x3C0)、
  EXPO(0x340-0x3BF, 与 XMP 槽 3/User1 互斥)。
- 原始 hex 编辑在左侧 hex 视图内**就地改**:点格子换成输入框 → `SetByte(off, val)`(高风险);
  旧的"偏移/值"表单已删除(功能重复)。
- **时序按时间或周期两种写法**(2026-09-21 v1.0.1): JEDEC 时序在 SPD 里是时间, 但控制器配置的
  是周期数 —— 界面两侧都要能看/能改。`Field.Hint` 显示当前值按 tCK 折算的周期数("16 clk",
  向上取整), 点击填进输入框; `SetField` 收 "16clk"/"16 clk"(×tCK 基准换算回 ns 再编码)或
  纯数字/"10ns"(按时间), 大小写不敏感。tCK 基准: JEDEC 字段用整片 dump 的 tCKmin
  (`EditState.tckNs`, 状态行显示 "1clk = X ns · Y MT/s"); XMP/EXPO 的 profile 时序用该
  profile 自己的 tCK —— profile 频率可以 != JEDEC 频率, 换算错了就是把频率写错。
  clk 输入是 profile 时序后缀**白名单**(voltage/commandRate 带 clk 直接报错, 防止换算结果
  被当成伏特写下去)。半周期输入(如 13.5clk)合法: 编码取最近可表示值, hint 按向上取整显示
  (实际生效 ≥ 请求值, 保守方向)。输入 ns 的**过程中**前端就按同一套 ceil 语义实时折算
  提示(基准: JEDEC 字段用 `EditState.tckNs`, profile 字段用缓存里的 `<前缀>.tCK` 值),
  提交后由后端 `Fields()` 给权威 hint; 所有编辑提交(字节/字段/CRC/重置)统一走
  `refreshAfterEdit()` 同步字段/hex/变更面板/SPD 信息四个视图。

### 全后端审计(2026-09-21, 真机写入链路跑通后)

三个新鲜上下文的子代理**并行、互不通气**只读审计三层(`eeprom`+`smbus` / `spd` / `app`),
结论交叉对照后逐条复核。完整问题表与证据在 `docs/离线验证报告.md` 第 3 节"第四轮",
这里只记**改动了既有约定的那几条**——它们会影响后续开发, 不要改回去:

1. **单页器件的分页不变式**: `pageCount()<=1` ⇒ `pageKnown=true`, 且 `setPage` 直接返回、
   `physOffset` 不做 SPA 切换。**任何情况下都不要对 256B 器件写 0x36** —— 它在单页器件上是
   SWP/PSWP 地址空间(DDR3 等单页器件会直接 NACK, 甚至有误改保护位的风险)。
2. **非 DDR5 的尺寸归一**: 尺寸 >512 又非 DDR5 时判为类型未知, 镜像归一成 512(不猜 DDR5 的 0x38 页选)。
3. **写周期延时按世代判定**(`smbus.needsWriteCycle`): DDR5 寄存器写不付 25ms; DDR4 及更早的 NVM 写才付。
4. **`NVMWrites` 的世代语义**: DDR4 上 `cmd==0 && val==0` 不算寄存器写, 必须计入 NVM 写;
   DDR5 的 MR11 页选则是寄存器写, 单独报"非 NVM 写"。
5. **控制器标识一律用 `ControllerInfo.Index`**(不是过滤后列表的下标): 前端 `option.value = c.index`。
   过滤(只列 `Devices>0`)与下标是两回事, 混用会连错控制器。
6. **`opMu` 下的"外层加锁/内部不加锁"约定**: 公开入口加锁后只能调 `*Locked` 内部函数
   (如 `SaveDump` → `dumpLocked`)。`deadlock_test.go` 会对**每个**对外入口做 5 秒超时守卫,
   违反约定会当场失败。
7. **安全门禁的位置早于一切副作用**: 目标 dump 的 CRC/世代/长度不合格时, 在
   **备份与写保护探测之前**就拒绝(`TestRejectedTargetIsProbedNever` 断言此时 NVM 写为 0)。
   备份仍早于任何探测写。
8. **`spd.SetField` 有世代门**: 字段键与目标 SPD 世代不符一律拒绝(DDR4 键不许落进 DDR5 结构,
   反之亦然), 且 `specValue` 全部带边界检查。
9. **恢复/复核路径只走逐字节读法**(`VerifyByteWise`): 块读/字读可能"快而假",
   不能用于确认写入结果或比对回滚。

### 编辑器与解析器的互相牵制(2026-09-21 第三轮)

编辑器(`editor_*.go`)与解析器(`ddr4.go`/`ddr5.go`/`ddr3.go`)是**两套独立实现**的偏移与
编码逻辑。`TestEditorAgreesWithParser` 让两边对同一根真实内存条给出同一个答案, 于是
"偏移表抄错"这类问题不再依赖人工核对 —— 实测把 DDR5 CL 偏移故意 +1 后该测试立即失败。

同时 `TestEditorFieldWritesStayInBounds` 钉住三条不变量:
1. 任何字段的写入都不得落在 CRC/校验和字节上;
2. 影响的字节数不得超过该字段自身宽度(否则说明偏移串到了别的字段);
3. 非时序字段"改回原值"必须逐字节复原(时序字段允许等价编码, 按时间等价判定)。

这一轮由此修掉的问题:
- **JEDEC CL 掩码在编辑器里缺失**(DDR4 bytes 20-23 / DDR5 bytes 24-28)——只有 XMP 的 CL 可编辑
- DDR4 CL 掩码的**低段/高段模式判断错**: 高段标志(byte23 bit7)是独立模式位, 旧实现
  只要列表里出现 ≥23 就切高段, 结果把同一份 dump 里的 CL10 判成非法
- `.present` 字段**不忠实**: 关闭 XMP/EXPO 原本只清启用位, 字段值读回来仍是 true;
  现在关闭会清掉 header magic(区块失效, profile 内容字节保留)
- `manufacturer`/`dramManufacturer` 传空串原本报错, 导致"改一次再撤销"失败; 现在空串 = 不改动
- 时序 no-op 容差从 1e-9 放到 6e-4 ns(界面显示精度): "把显示值填回去"现在保证不写字节

## 9.6 读速的真正瓶颈: 模块的"等待模式"(2026-09-21 定位)

真机(AMD FCH 790b:1002, SMBus 396kHz)实测:逐字节 1024B 要 **32.145s**,字读(2B/事务)
**16.509s** —— 即"每次事务固定 ~31ms",与字节数无关。对比 Thaiphoon Burner 读同一条只要 **0.2s**。

把 PawnIO 上游模块源码(`SmbusPIIX4.p` + `sleepmode.inc`)读了一遍,原因很清楚:

```
piix4_transaction(size):
    microsleep_long(((10 + 9*size) * timing * 4) / 66)   // 整笔事务的预估等待
    do { microsleep_short((timing*4)/66); ... } while (...)  // 每拍轮询状态
```

`sleepmode.inc` 里两种等待各有两套实现:

| 模式 | microsleep_long | microsleep_short |
|---|---|---|
| `AlwaysBusy`(0) | `microsleep2`(忙等, µs 精确) | `microsleep2` |
| `ShortBusy`(1) | `microsleep`(线程休眠) | `microsleep2` |
| `AlwaysSleep`(2) | `microsleep`(线程休眠) | `microsleep`(线程休眠) |

`microsleep` 走 Windows 线程休眠 → 粒度是一个时钟中断(**约 15.6ms**)。OpenRGB 用 `AlwaysSleep`
是为了省 CPU(它不做整片读),照抄过来就成了:一次事务 ≥1 个中断,轮询再一个 → **≈31ms/事务**,
1024 字节 512 次事务 = 16 秒。**这就是 16s/32s 的全部来源。**

改成 `AlwaysBusy`(忙等)后回到真实总线时间:396kHz 下一次 2 字节读 ≈
`(10+9*4)*166.8/66 ≈ 116µs`,512 次 ≈ 60ms + ioctl 开销;块读(32B/事务)更快。
忙等的 CPU 代价只有百毫秒级,完全可接受。

同时把模块的 `ioctl_clock_freq`(读/写 SMBus 时钟)接出来:界面与日志显示实际时钟,
便于核对(用户报告 396kHz 与 BIOS 设定一致)。

> 结论: 软件层的 `ReadDelay`(1ms/字节)只占约 1s,之前"减少事务数"的方向(块读→字读)
> 是对的但不是主因;主因是等待模式。两件事都已修:三级读回退 + 忙等默认。
