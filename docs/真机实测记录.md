## 2026-09-22 · i3-7100 首测: 读取 OK, 写入被 NACK(Win32 433 = ERROR_NO_SUCH_DEVICE)

用户提供 18 行完整启动+读取+保护状态日志, 摘录关键行:

```
发现 1 个 SMBus 控制器(其中有设备的 1 个)      ← 单一 i801, 无重复枚举(v1.0.1 修复生效)
已连接 Intel PCH i801 (IO:F040)
探测 0x50 在线(byte0=0x23) · 扫描完成: 1 个设备
总线环境: SMBus 100.0kHz, 忙等(最快)
已选择 0x50 (非DDR5, 512 字节)
读取 512 字节: 逐字节(1 字节/事务); 事务 512 次, 耗时 1.345s(等待 514 ms)
已备份当前 SPD: C:\Users\test\Desktop\backup\spd-0x50-20260922-162307.bin (512 字节)
保护状态查询: 块 0..3 写测试失败: 写入 0x0/0x80/0x100/0x180 失败(SMBus 操作失败(Win32 错误 433)), 且还原也失败
保护状态: 受保护 B0,B1,B2,B3 · PSWP 不适用
```

**结论与数据点**:

1. **读取路径正常**(首个 I801 数据点): 512 字节逐字节读 512 事务 1.345s @100kHz(其中等待 514ms)。
   与 AMD(392.9kHz 字读 512 事务 109ms)相比, 事务数相同但时钟低 4 倍 —— 时间基本由时钟决定。
   I801 这条路径没走块读/字读, 读档位自适应按预期降级到逐字节。
2. **备份目录生效**: `C:\Users\test\Desktop\backup\`(程序同级自动创建), 符合 v1.0.1 约定。
3. **写入被 NACK(根因已查清)**: 4 个块首的写测试, 写(取反值)与还原写都返回 `Win32 错误 433`。

   **433 = `ERROR_NO_SUCH_DEVICE`("器件未应答") —— 它就是 `STATUS_NO_SUCH_DEVICE (0xC000000E)`
   的 Win32 命名空间形态**(`HRESULT_FROM_WIN32(433) = 0x800701B1`)。也就是说: 这些写**本来就是 NACK**,
   控制器/器件直接不应答, 一个字节都没写进去。参考:
   [nmap#1948 对 433 的定位](https://github.com/nmap/nmap/issues/1948)、
   [MS 系统错误码 0-499(433 未列在该页, 但常量在 winerror.h)](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--0-499-)。

   `internal/smbus` 原本只把 NTSTATUS `0xC000000E` 映射成"NACK"文案, **不认识 Win32 的 433**,
   于是 `eeprom.isNACK()` 匹配不到 "NACK"/"无响应", 把它当成"非 NACK 错误(写可能已生效)"处理 ——
   这才是那串"还原也失败 / 字节可能停在取反值"告警的来源。**误报, 实际内容从未改变。**

   真正原因:**已确认是 BIOS 锁定 SPD 写**(2026-09-22 用户回执):
   - [Thaiphoon Burner(台风)](http://www.softnology.biz/) 读 SPD 详情页同样显示 **BIOS 锁定写保护**, 与本工具判断一致(独立交叉验证);
   - 用户进 BIOS 逐项查找 **没有** `SPD Write Disable` / `SPD 写保护` 相关选项 —— 该品牌机默认锁定且不提供开关;
   - 结论: 该平台为**只读平台**(读取/编辑/校验/导出可用, 写入与写保护操作被平台拒绝),
     与本工具实现无关; 要写入需换平台或用编程器(CH341A 等)离线写。

4. **本次修复(4 项, 含根因)**:
   - **根因**: `win32Err(433)` 映射为带 "NACK" 的文案(`设备无响应 NACK(0x800701B1 / Win32 433)`),
     写测试据此判定"受保护、内容未变", 不再尝试还原写、不再产生误导告警;
   - 写失败 + 还原失败时**回读核实**: 内容未变就明确说"无需用备份恢复";
   - 汇总行区分 **受保护**(写测试确认被拒)与 **未知/不可写**(写测试未能生效), 不再把未知说成受保护;
   - 平台已报告 BIOS SPD 写禁止时**跳过写测试**(一个字节都不写)直接给结论;
   - DDR5 遇平台锁写**不短路**(它本来就是纯读 MR12/MR13 位图, 器件侧信息有价值),
     但补一条提示"显示开放 ≠ 可写", 避免面板显示全部开放而写入被拒时被当成工具缺陷。

**结论(用户已确认)**: BIOS 锁定 SPD 写, 且 BIOS 内**没有**对应开关 —— 本平台记为**只读平台**。
新增的处置路径已写进 `docs/写入操作手册.md` 的"只读模式(BIOS 锁定 SPD 写)怎么办":
进 BIOS 找 `SPD Write Disable` → 找不到则换平台写入或用编程器离线写; 界面侧连上即常驻只读横幅。

## 2026-09-22 追加: "DDR4 被读成 256B/未知世代" 根因(i3-7100, 已修)

现象: 在 i3-7100 上点过一次"保护状态查询"后, 重新选择设备报
`解析失败: Error: 不支持的世代 未知(0x0)`, 整片只读 256 字节; 换任何版本的 exe 都复现。

根因链:
1. DDR4(EE1004)偏移 0x00-0xFF 读的是**当前页**; 保护状态查询的块首写测试要翻到
   第 2 页(块 2/3 = 0x100/0x180), 查询结束后页停在第 2 页且无人复位。
2. 类型探测裸读 byte2 —— 拿到的是第 258 字节(0x00) → 判成"未知类型" → 按 256B 读。

修复(8643c7b): 探测读出未知类型时先发 SPA(0x36) 选回页 0 重读(自愈, 外部软件如
台风留下的页残留同样被兜住); ReadAll / 逐字节复核 / 保护状态查询收尾一律归零
(已在页 0 时不发总线命令); 0x56(SA=6)不做页复位尝试(0x36 在 SWP/PSWP 地址空间,
宁可报未知也不冒险写)。DDR5 探测/状态查询走 MR 空间不受影响; 256B 单页器件无此问题。

### 第五轮: 保护状态全开放 + 写入档位/回读路径加固

| 项 | 结果 | 原始证据 |
|---|---|---|
| 写保护状态 | **16 块全部开放**, MR12=0x00 MR13=0x00, PSWP 不适用 | `保护状态: B0=开放 … B15=开放 | MR12=0x00 MR13=0x00` |
| 上游实现核对 | 逐字节写 + `(off%128)|0x80` + MR11 切页 + MR12/13 位图, 与我们一致 | [Eeprom.cs](https://raw.githubusercontent.com/1a2m3/SPD-Reader-Writer/master/src/SpdReaderWriterCore/Eeprom.cs) `Write()` / `AdjustOffset()` / `GetRswp()` |

**推论**: RSWP 不是首写失败的原因。同时"平台禁止一切 SPD 写"也基本排除 —— 读整片要切 8 次页,
而切页就是对 0x50 的寄存器写(MR11), 那些写是成功的。因此怀疑点收敛到: (1) 该 hub 只认块写、
逐字节写被忽略; (2) 回读走了块读/字读路径导致"写成功却误判为被忽略"。两者本轮都已加固:
写入档位会自动切到块写(协议 5), 回读固定用最原始的逐字节读。

### 第六轮: **写入能力探测通过**(真机首次确认真实 NVM 写生效)

```

             然后对 0x22B 写反值 0xff 再还原(该字节不在 CRC 覆盖范围内)

```

这条同时证明了四件事:

1. **该平台/该条的 NVM 逐字节写是通的**(协议 2, cmd = 0x80|0x2B, 页 4) —— 不是"只能全量写",
   也不是平台级 SPD 写保护;
2. 探测的**目标选择正确**: 挑中了 0x22B(厂商特定区, 不在任何 CRC 覆盖范围内, 断电也不破坏 CRC);
3. 探测的**还原 + 整片复核链路有效**(写完反值又写回原值, 整片比对通过);
4. 因此之前的"写入没生效"**不是硬件拒绝写入**, 而是写入流程里某一层的问题。

剩余怀疑点(按可能性):
- 旧版**回读走块读/字读路径**导致"写成功却回读不一致"的假失败 → 已在 `8ccbf296` 起改为
  回读固定用最原始的逐字节读;
- 编辑的字节**落在 CRC 覆盖范围内却没有重算 CRC** → 预检会正确阻断(`目标文件 CRC 校验不通过`),
  此时设备内容当然不变 —— 现象与"没生效"一致, 需要那一行日志确认。
