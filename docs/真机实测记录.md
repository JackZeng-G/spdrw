### 读速对照(同一根条)

| 档位 | 每事务 | 事务数 | 实测耗时 |
|---|---|---|---|
| 块读(协议 5, 32B) | 32B | 33 | — **被 NACK, 本机不可用** |
| 字读(协议 3, 2B) | 2B | 512 | **16.509s**(实测) |
| 逐字节(协议 2, 1B) | 1B | 1024 | 32.145s(实测, 上一版) |

换算: 单次事务 ≈ 32ms, 与字节数无关 → **提速只能靠减少事务数**。
512 次事务已接近"2 字节协议"的物理上限;再快要等平台/驱动支持块读(I801 路径实现了块读, 本机走 PIIX4 无解)。

### 第二轮(同日)

| 项 | 结论 | 原始证据 |
|---|---|---|
| 读速(字读档) | 1024B: 事务 512 / **16.509s**(上一版逐字节 32.145s) | `读取 1024 字节: 字读(2 字节/事务); 事务 512 次, 耗时 16.509s(等待 2 ms)` |
| 编辑器改字节 | 正常, hex 按十六进制解析 | `原始编辑: 0x203 = 0x24` / `0x203 = 0x5A` |
| HUB 诊断行 | `MR0=51 MR3=86 MR11=07 MR29=03 MR48=80` | 读取后自动打印 |

> 注: `0x203` 属于 DDR5 的**生产日期**字节(身份区 0x200-0x27F), 不在任何 CRC 覆盖范围内 ——
> 这一轮据此加了"改动是否影响校验"的区分: 该类改动不再提示"记得重算 CRC", 左侧 hex 也会标蓝。

### 第三轮: 读速瓶颈定位(同日, 用户提供 Thaiphoon 对比)

| 项 | 数值 | 来源 |
|---|---|---|
| 本工具(逐字节) | 1024B / 32.145s | 真机日志 |
| 本工具(字读 2B/事务) | 1024B / 16.509s | 真机日志 |
| **Thaiphoon Burner** | **1024B / 0.2s** | 用户实测 |
| SMBus 时钟 | **396 kHz** | 用户读寄存器 |
| 控制器 | **790b:1002**(AMD FCH, PIIX4 路径) | 用户 |

**结论**: 每次事务固定 ~31ms = 两个 Windows 时钟中断(15.6ms ×2)。根因是 PawnIO 模块的
等待模式 `AlwaysSleep`(照抄 OpenRGB 的省 CPU 设置):整笔事务的预估等待与每拍状态轮询都
交给线程休眠。改成 `AlwaysBusy`(忙等)后,396kHz 下一次 2 字节读的真实总线时间约 116µs。

**待用户验证**: 新 exe 读取 1024B 的耗时(预期从 16.5s 降到 1s 以内;若块读能通还要更快),
以及日志/面板里显示的 `SMBus 396.0kHz, 忙等(最快)`。

### 第四轮: 读速修复确认 + V2 干跑通过 + 首次真写失败

| 项 | 结果 | 原始证据 |
|---|---|---|
| 读速(忙等) | 1024B / **334ms**(333ms), 字读 2B/事务 × 512 | `读取 1024 字节: 字读(2 字节/事务); 事务 512 次, 耗时 334ms(等待 2 ms); SMBus 392.9kHz, 忙等(最快)` |
| 总线环境 | 392.9 kHz, 忙等 | 同上 |
| **V2 干跑** | **零写入 ✓** | `干跑完成: 将写入 1 字节; 期间总线事务: 读 534 次 / 页选择与命令写 0 次 / 字节写 8 次, 其中对 SPD NVM 的数据写 0 次(零写入)` |
| 首次真写(单字节) | **失败并回滚**(用户"好像没生效") | 日志出现"已重新读取设备/编辑器里仍是你的目标内容"(= 失败分支); 但 `写入失败: …` 那行未被回帖 |

> 读速提升 **49 倍**(16.509s → 334ms), 与 Thaiphoon 的 0.2s 同量级。
> 干跑那 8 次"字节写"是 8 个页的 MR11 切页(非 NVM 写), 已改为单列"非 NVM 写"以免误读。
> 首次真写失败的**具体原因待定**: 需要那一行 `写入失败: …`(含本版新增的"现场: 0x…(页…, cmd…) MR11/12/13/29/48/52"快照),
> 或"检测写入能力"按钮的结论。已知: 平台级的 MR11 寄存器写是成功的(读整片要切 8 次页),
> 所以"平台禁止一切 SPD 写"不成立, 更可能是 hub 侧不落地 NVM 写入或该块被保护。

### 第五轮: 保护状态全开放 + 写入档位/回读路径加固

| 项 | 结果 | 原始证据 |
|---|---|---|
| 写保护状态 | **16 块全部开放**, MR12=0x00 MR13=0x00, PSWP 不适用 | `保护状态: B0=开放 … B15=开放 | MR12=0x00 MR13=0x00` |
| 参考实现核对 | 逐字节写 + `(off%128)|0x80` + MR11 切页 + MR12/13 位图, 与我们一致 | [Eeprom.cs](https://raw.githubusercontent.com/1a2m3/SPD-Reader-Writer/master/src/SpdReaderWriterCore/Eeprom.cs) `Write()` / `AdjustOffset()` / `GetRswp()` |

**推论**: RSWP 不是首写失败的原因。同时"平台禁止一切 SPD 写"也基本排除 —— 读整片要切 8 次页,
而切页就是对 0x50 的寄存器写(MR11), 那些写是成功的。因此怀疑点收敛到: (1) 该 hub 只认块写、
逐字节写被忽略; (2) 回读走了块读/字读路径导致"写成功却误判为被忽略"。两者本轮都已加固:
写入档位会自动切到块写(协议 5), 回读固定用最原始的逐字节读。

### 第六轮: **写入能力探测通过**(真机首次确认真实 NVM 写生效)

```
写入能力探测: 先备份当前内容(C:\Users\<user>\.spdrw\backups\spd-0x50-20260920-202132.…bin),
             然后对 0x22B 写反值 0xff 再还原(该字节不在 CRC 覆盖范围内)
写入能力探测结果: ok(逐字节写生效: 0x22B 从 0x00 变成 0xff(该条可写); 已还原=true, 整片复核=true)
```

这条同时证明了四件事:

1. **该平台/该条的 NVM 逐字节写是通的**(协议 2, cmd = 0x80|0x2B, 页 4) —— 不是"只能全量写",
   也不是平台级 SPD 写保护;
2. 探测的**目标选择正确**: 挑中了 0x22B(厂商特定区, 不在任何 CRC 覆盖范围内, 断电也不破坏 CRC);
3. 探测的**还原 + 整片复核链路有效**(写完反值又写回原值, 整片比对通过);
4. 因此之前的"写入没生效"**不是硬件拒绝写入**, 而是写入流程里某一层的问题。

剩余怀疑点(按可能性):
- 旧版**回读走块读/字读路径**导致"写成功却回读不一致"的假失败 → 已在 `e8469901` 起改为
  回读固定用最原始的逐字节读;
- 编辑的字节**落在 CRC 覆盖范围内却没有重算 CRC** → 预检会正确阻断(`目标文件 CRC 校验不通过`),
  此时设备内容当然不变 —— 现象与"没生效"一致, 需要那一行日志确认。

### 第七轮: **真机首次真实写入成功(V3 通过)**

```
写入并校验通过: 1 字节(备份 C:\Users\<user>\.spdrw\backups\spd-0x50-20260920-202418.969373600.bin;
  写入档位 单字节(协议 2)); 校验: 每个字节写完即回读 1/1 + 整片 1024 字节比对 +
  整片逐字节复核(关掉块读/字读, 独立读法); 总线: 读 3689 / 字节写 50(其中 NVM 1)
```

逐项核对:

| 项 | 期望 | 实测 |
|---|---|---|
| 写入字节数 | 1(增量模式只写改动的字节) | 1 |
| **NVM 数据写** | **恰好 1** | **1** ✓ |
| 写入档位 | 单字节(协议 2) | 单字节(协议 2) ✓ |
| 逐字节回读 | 1/1 一致 | 1/1 ✓ |
| 整片比对 | 1024 字节一致 | ✓ |
| 整片逐字节复核(独立读法) | 一致 | ✓ |
| 写入前备份 | 有 | 有(路径见日志) ✓ |

`字节写 50 = 48 次切页(6 次整片读 × 8 页) + 1 次 NVM 数据写 + 1` —— 与"非 NVM 写"的语义一致。
`读 3689` 是本次操作所有整片读(备份/预检/计划/回读/整片比对/逐字节复核/失败后重读)之和。

追加(同日): 编辑器里的**独立复核**也通过 —— `与设备比对: 逐字节一致(校验通过)`;
随后又写了第二个字节(0x207)同样成功(`写入并校验通过: 1 字节 … NVM 1`)。
另外发现并修掉一个界面问题: **切换设备后后端编辑器已被清空, 而前端仍显示上一根条的内容**
(点"与设备比对"报 `编辑器尚未载入数据` 就是这么来的)。现在切设备会同步复位编辑器视图并明确
提示"编辑器内容已失效, 需要重新从设备载入", 操作类按钮(放弃修改/重算 CRC/另存/比对/写入)
只有真载入后才可用 —— 避免把 A 条的改动误以为在操作 B 条。

> 结论: **V2(干跑零写入)与 V3(单字节真写 + 三层校验)都在真机上通过**。
> 之前那次"没生效"由此可判定为流程层问题(最可能是旧版回读走块读/字读路径的假失败),
> 已在 `e8469901` 修复并被本次结果验证。
